# ROADMAP — starmap как сервис генерации карт неба

> Этот файл — исходный план, написанный до реализации сервиса. Сервис реализован полностью
> (см. `CLAUDE.md`, `API.md`, `README.md`); чекбоксы ниже актуализированы по факту. Реально
> открытые задачи — в разделе «Осталось сделать» в самом низу.

## Цель

Сейчас `main.py` — это **одноразовый скрипт**: при запуске грузит все данные, рисует
одну фиксированную карту всего неба (RA/DEC, 6000px) и сохраняет `map_big.png`.

Нужно превратить репозиторий в **долгоживущий сервис**, который:
- запускается один раз и держится в памяти (данные загружены заранее);
- слушает запросы от Telegram-бота через **MQTT**;
- генерирует карту под параметры запроса (местоположение / время / тип карты);
- отдаёт готовое изображение обратно боту;
- публикует свой статус доступности, чтобы бот знал, запущен сервис или нет.

Транспорт — **MQTT** (брокер уже работает на Raspberry Pi, бот к нему подключён,
паттерн «запрос/ответ + картинка в base64» в боте уже реализован для `/photo`).

Развёртывание на Pi — **без Docker** (Docker только для локальной разработки).

## Контракт с ботом (зафиксировать первым делом)

Это договор между двумя репозиториями — он не должен меняться в одностороннем порядке.

### Топики MQTT

| Топик | Направление | Назначение |
|-------|-------------|------------|
| `starmap/command` | бот → сервис | запрос на генерацию карты |
| `starmap/result`  | сервис → бот | готовая карта или ошибка |
| `starmap/status`  | сервис → бот | `online` / `offline` (**retained + LWT**) |

### Запрос (`starmap/command`)

```json
{
  "request_id": "1718635200",
  "lat": 55.75,
  "lon": 37.62,
  "datetime": "2026-06-17T22:00:00",
  "map_type": "horizon"
}
```

- `request_id` — обязателен, по нему бот сматчит ответ (механика `register_request` уже есть в боте).
- `lat` / `lon` — координаты наблюдателя.
- `datetime` — опционально, ISO8601; по умолчанию «сейчас».
- `map_type` — тип карты (см. раздел «Типы карт»).

### Ответ (`starmap/result`)

```json
{
  "request_id": "1718635200",
  "status": "ok",
  "image_base64": "..."
}
```

либо при ошибке:

```json
{
  "request_id": "1718635200",
  "status": "error",
  "error": "Краткое описание проблемы"
}
```

> Альтернатива base64 (оба сервиса на одном Pi): сохранять PNG в общий каталог и
> слать в ответе только путь (`"image_path": "/var/lib/starmap/out/<request_id>.png"`),
> бот читает файл с диска. Меньше нагрузка на брокер и память. Решение можно отложить —
> начать с base64 (меньше движущихся частей), перейти на путь при упоре в размер.

### Статус (`starmap/status`)

- При старте сервис публикует **retained** `{"status":"online"}`.
- В **LWT** регистрирует `{"status":"offline"}` — брокер сам разошлёт его, если сервис упадёт.
- При штатном завершении — публикует `offline` перед disconnect.

## Задачи

### 1. Конфигурация
- [x] `src/config.py`: `MQTT_BROKER`, `MQTT_PORT`, топики, путь к каталогу вывода, дефолтное
      разрешение, уровень логирования — всё читается из `config/config.yaml` с переопределением
      через env-переменные.
- [x] Завести `.env.example`.
- [x] Настроить логирование (`logging`), без `print`.

### 2. Загрузка данных один раз на старте
- [x] Инициализация стиля и загрузка тяжёлых данных (`stars...parquet`, `de421.bsp`, `ongc...`
      и т.д.) происходит один раз при старте `Renderer`, до входа в MQTT-цикл.
- [x] starplot не перечитывает parquet/bsp на каждый рендер (DuckDB-backend лениво грузит и
      держит каталоги в памяти на весь жизненный цикл сервиса).
- [x] `MPLBACKEND=Agg` зафиксирован (systemd unit, Dockerfile, `install.sh`).

### 3. Рендер с параметрами (главная содержательная работа)
- [x] Логика вынесена в `Renderer.render(RenderRequest) -> bytes` (`src/renderer.py`).
- [x] Экспорт в память (`BytesIO`) — запись на диск делает отдельно `src/storage.py` в
      file-режиме.
- [x] `render.resolution` в `config.yaml` по умолчанию ниже 6000px (см. `README.md`).
- [x] Привязка к местоположению/времени наблюдателя реализована для `zenith`/`horizon`/`optic`
      через starplot `Observer`; `full`/`galactic` — без наблюдателя (по дизайну).

#### Типы карт (`map_type`)
- [x] `full` — полносферная RA/DEC карта (`MapPlot`, Miller).
- [x] `galactic` — всё небо в галактических координатах (`GalaxyPlot`, Mollweide).
- [x] `zenith` — купол неба над наблюдателем (`ZenithPlot` + `.horizon()`; `.info()` не вызывается,
      см. примечание ниже про баг в starplot 0.20.4).
- [x] `horizon` — вид над горизонтом из точки наблюдателя (`HorizonPlot`); направление через `options.direction`.
- [x] `optic` — объект в конкретную оптику (`OpticPlot`); бинокль/телескоп/камера.
- [x] `optic`: резолв имени объекта (`target.object`) в ra/dec — каталожные номера (`M31`/`NGC224`/`IC1396`
      в любом написании), Солнце/Луна/планеты, звёзды по имени, общие названия DSO (`_resolve_object_name`,
      `src/renderer.py`); `target.ra`/`target.dec` по-прежнему принимаются напрямую.
- [ ] Локализация подписей на русский (`settings.language = "ru"` — включить и проверить поддержку в starplot).
- [x] **Прогон рендеров вживую в Docker** (2026-06-17): все 5 типов рендерятся корректно (starplot 0.20.4).
      Найдено и исправлено: `settings.data_path` должен быть `Path` (не `str`); `ZenithPlot.info()`
      сломан в 0.20.4 (обращается к `self.dt`) — вызов убран; `wait_for_publish` на shutdown мог
      падать при разрыве — обёрнут в try/except.
- [ ] **base64 inline не лезет в MQTT** для больших карт (oversize packet → залипание на QoS1 retry).
      Перешли на `output.mode = file` по умолчанию. Если нужен base64 — добавить size-guard, чтобы
      oversize отдавал ошибку, а не вешал соединение.

### 4. MQTT-сервис
- [x] `src/service.py`: единый клиент paho-mqtt.
- [x] `on_connect` → подписка на `starmap/command` (qos=1) + публикация retained `online`.
- [x] **LWT** настроен (`will_set` на `starmap/status` = `offline`, retained).
- [x] `on_message` → парсинг JSON через `parse_command`, валидация, постановка в очередь.
- [x] Публикация ответа в `starmap/result` с тем же `request_id` (`queued`/`ok`/`error`).
- [x] Reconnect обрабатывается paho-mqtt's `loop_start`/встроенным reconnect.
- [x] Сетевой цикл клиента работает в фоне сервиса (см. `main.py`/`service.py`).

### 5. Конкурентность и устойчивость
- [x] **Один рендер за раз**: реализовано через однопоточный worker, читающий ограниченную FIFO
      `queue.Queue` (не через `threading.Lock`) — см. `src/service.py`.
- [x] Стратегия выбрана: короткая ограниченная очередь (`config.QUEUE_MAX_SIZE`); при
      переполнении — `error: "queue full, try again later"` (вместо `busy`).
- [x] Генерация обёрнута в try/except; при сбое — `status: error`, сервис не падает.
- [x] Тайм-бюджет ~90–120с учтён при выборе разрешения по умолчанию (см. `README.md`).

### 6. Управление выводом

      количеству/возрасту (`output.retention`).
